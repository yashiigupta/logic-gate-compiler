# Viva notes: explaining the project in two minutes

**One-line pitch:** "We built a compiler that takes boolean equations and turns them into
a hardware description (Verilog), a truth table and a circuit diagram. It shows the
output of each of the six compiler phases."

Use this running example the whole way through:

```
INPUT a, b, c;
OUTPUT out;
out = (a AND b) OR NOT c;
```

## 1. Lexical analysis (`lexer.js`)
- Reads characters and groups them into **tokens**: `INPUT`, `IDENTIFIER(a)`, `COMMA`, `AND`, `LPAREN`…
- Skips whitespace and comments. Keywords are case-insensitive.
- **Errors:** an unknown character (`&` gets the hint "did you mean AND?") or a constant other than 0/1.
- Each token stores its line and column, so every later error can point to the exact spot.

## 2. Syntax analysis (`parser.js`)
- A **recursive-descent parser** with one function per grammar rule.
- Precedence comes from the grammar itself: `or_expr → xor_expr → and_expr → not_expr → primary`.
  The lower the rule, the higher its precedence, so `NOT` binds tightest.
- Builds an **AST**: `=` → [`out`, `OR` → [`AND`(a,b), `NOT`(c)]].
- **Panic-mode recovery:** after an error it skips to the next `;` and keeps parsing, so all syntax errors are reported at once.

## 3. Semantic analysis (`semantic.js`)
- Builds the **symbol table**: name, kind (input/output/wire), type (1-bit), and the lines where each signal is declared, assigned and used.
- Checks "is this allowed?": undefined signal, use before assignment, output assigned twice,
  assigning to an input, output never assigned, duplicate declaration, reserved names.
- Because every signal is assigned exactly once and only after its inputs exist, the circuit **cannot contain loops**.

## 4. Intermediate code (`ir.js`)
- **Three-address code**: at most one operator per line.
  ```
  t1 = a AND b
  t2 = NOT c
  out = t1 OR t2
  ```
- Generated by a **post-order walk** of the AST: children first, then the parent.
- Includes a small **IR interpreter** (`runIR`) that executes the code. It is used for the truth table.

## 5. Optimization (`optimizer.js`)
Three passes run repeatedly until nothing changes (a fixed point):
1. **Constant folding and boolean algebra laws:** identity, annihilator, idempotent, double negation, plus copy propagation.
2. **Common sub-expression elimination:** `a AND b` computed twice becomes one reuse. Operands are sorted first because AND, OR and XOR are commutative.
3. **Dead code elimination:** a backward walk from the outputs. Anything that never reaches an output is deleted.

Each IR instruction is one gate, so **fewer instructions means fewer gates**.

## 6. Code generation (`codegen.js`)
- **Target code:** a Verilog module (`assign out = t1 | t2;`).
- **Truth table:** runs the IR for all 2ⁿ input combinations.
- **Correctness proof:** the truth table is computed from both the original and the optimized IR. If every row matches, the optimizer preserved the meaning.
- **Circuit diagram** (`ui/diagrams.js`): each instruction is a gate. A gate's column = 1 + the deepest of its inputs.

## Likely questions
- *Why recursive descent?* It's simple, every grammar rule maps to one function, and it handles precedence naturally. (The grammar has no left recursion.)
- *What is the difference between a parse tree and an AST?* An AST drops syntax-only tokens such as `(`, `)` and `;` and keeps only the meaning.
- *Why three-address code?* It is easy to optimize and maps one-to-one onto logic gates.
- *How do you know the optimizer is correct?* The equivalence check on the truth table (shown in the UI with a green ✔) and the automated tests (`node tests/run_tests.js`).
